# BUG-123 글 대화에서 ‘대답 중…’이 뜨면 입력칸 아래로 스크롤됨

- 상태 `fixed` · 심각도 S3 · 우선순위 P1 · 유형 화면 명세 누락 및 구현 · 원인 08·11단계 · TC-651 실기기 확인 대기
- 발견 2026-11-24 03:38 KST, 운영 iPhone Safari 글 대화. 사용자님 제보는 “야 근데 웹에서 하나 대화 보내면 무한스크롤 됨”이에요. 03:37에 찍힌 화면에는 ‘읽음’, ‘대답 중…’, 입력칸 아래 빈 공간이 보여요.
- 기준 [SPEC-124·148·149와 SCR-107](../app-chat.md#scr-107-글-대화의-스크롤). 화면 정의에 스크롤 영역과 ‘대답 중…’이 표시되는 동안의 동작을 명시했어요.

## 재현과 원인

최신 `main` 기준 `5f89fd5`의 실제 웹 파일과 합성 로컬 API를 Playwright WebKit의 iPhone 13 프로필로 열어요. 과거 메시지가 있는 방에서 한 줄을 보내고 가짜 서버가 ‘읽음’과 ‘대답 중…’을 보낸 동안 입력칸 아래로 스크롤해요. Windows WebKit에서 가로 390px을 유지하며 뷰포트 높이를 664px에서 430px로 줄였다 복원해 키보드 전환을 모사해요. iOS 키보드와 Safari 주소 막대의 동작은 실기기에서 확인해요.

| 수정 전 상태 | 문서 스크롤 위치 | 문서 높이 | `visualViewport.height` | 메시지 목록 스크롤 위치 |
| --- | ---: | ---: | ---: | ---: |
| 첫 화면 | 0px | 664px | 664px | 1,728px |
| ‘읽음’과 ‘대답 중…’ 표시 | 0px | 2,434px | 664px | 1,864px |
| 같은 상태, 키보드 높이 모사 | 0px | 2,434px | 430px | 2,098px |
| 키보드 닫힘을 모사한 뒤 문서 끝으로 스크롤 | 1,770px | 2,434px | 664px | 1,864px |
| 답 도착 | 0px | 664px | 664px | 1,873px |

입력 없이 기다리는 동안 자동으로 계속 내려가는 움직임은 관찰되지 않았어요. 빈 공간은 화면 낭독기용 문구 `.sr-only`가 절대 위치로 배치될 때 생겼어요. 목록에 위치 기준이 없어 문구의 영역이 목록의 스크롤 경계를 벗어나 문서 높이를 늘렸어요. 답이 도착해 표시가 사라지면 문서 높이가 돌아와요.

## 변경 이력과 영향 범위

- 읽음·대답 중 표시를 추가한 `b33e5bc`부터 같은 절대 위치 문구와 목록 스타일이 함께 있었어요. 이력은 코드가 들어온 시점을 보여요.
- 0.3.4 버전 PR #110은 앱 버전 설정을 바꿨어요. 앞선 PR #108은 공유 글 대화에 앱 전용 업데이트 배너를 추가했어요. 목록의 스크롤 규칙과 화면 낭독기용 문구는 두 PR 모두에서 그대로였어요. PR #115는 통화 자산, #116은 관리 기능, #117은 관리 페이지와 `unified.css`를 바꿨어요. 세 PR의 병합 전후에 `chat.css`·`chat.js`·글 대화 `index.html` 변경은 없어요.
- Android 0.3.4의 `ChatActivity`도 서버의 `/chat/`을 WebView에서 열어요. 같은 HTML·CSS를 받아요. Android 기기에서 같은 스크롤 증상이 있었는지는 확인이 필요해요.
- 운영에서 활성 상태인 `marong-app.service`의 실행 경로를 읽기 전용으로 확인했어요. 해당 소스 폴더의 `chat.css`·`index.html`·`chat.js` 세 파일 SHA256이 기준 `5f89fd5`와 일치했어요.

## 회귀 시험과 실기기 확인

- **TC-650 (e2e)**: iPhone WebKit에서 키보드 전환 모사 유무 두 경우를 확인해요. ‘읽음’과 ‘대답 중…’이 나타나고, 같은 상태의 대기 응답을 받아도 화면이 스스로 움직이지 않아요. 문서를 아래로 스크롤해도 위치는 0이며, 보낸 글·대답 중 표시·답은 목록 끝에서 이어지고 입력칸은 목록 아래에 보여요.
- **TC-651 (device)**: 수정본이 제공되는 iPhone Safari에서 대화가 충분히 있는 방을 열어요. 키보드를 띄워 한 줄을 보낸 뒤 ‘대답 중…’이 보일 때 목록과 입력칸 아래를 각각 밀어 봐요. 키보드를 닫고 다시 열어 입력칸, 주소 막대 전환, 답이 올 때의 목록 위치를 확인해요. iOS·Safari 버전과 재현 여부를 기록해요. 실기기 확인 대기예요.
- 기존 TC-132·157은 Chromium에서 메시지 상태와 표시를 확인했어요. WebKit에서 답변 대기 중 문서 높이와 스크롤을 측정하지 않아 놓쳤어요. TC-650에서 이 조건을 검사해요.

### 로컬 실행 결과

`node --test apps/android/test/chat-scroll.e2e.cjs`를 Playwright 1.65.1과 WebKit으로 실행했어요. 수정 전 `ab29c7c`은 2/2 실패했어요. 두 경우 모두 문서가 2,434px까지 커졌고 250px 스크롤 시도 후 위치가 250px이었어요. 수정 `420934f`에서 목록에 `position: relative`를 줘 낭독 문구의 배치 기준을 목록에 두고 같은 시험 2/2를 통과했어요. 대답 중 문서 높이는 뷰포트와 같은 664px 또는 430px이었고, 키보드를 닫은 뒤 664px로 돌아왔어요. 스크롤 시도 뒤에도 문서 위치는 0px이었고, 같은 상태의 대기 응답을 받은 전후에 목록 위치가 같았어요.

관련 브라우저 시험 파일 8개를 `node --test --test-concurrency=1`로 실행해 64/64 통과했어요. 첫 병렬 실행에서 업데이트 배너 TC-618의 3초 표시 시간 검사가 한 번 실패했고, 해당 시간 검사만 다시 실행했을 때 2/2, 전체 직렬 재실행에서 64/64가 통과했어요. 격리 Postgres 글 대화 서버 검사 `tests/test_app_chat.py`는 377개 확인을 통과했어요. `npm test --prefix apps/android`는 34개 통과했고 릴리스 병합 매니페스트 검사 1개는 빌드 산출물이 없어 실행하지 못했어요.
