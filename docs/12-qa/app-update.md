## BUG-112 다운로드한 업데이트의 설치 지연

- 상태 `fixed`, 심각도 S3. 자동 설치가 지연되며, 인증된 다운로드를 다시 받아 수동 설치할 수 있어요. 고침은 2026-11-23 PR #100(`5634406`)으로 합쳐졌고 0.3.3(버전 코드 11, PR #106)으로 게시됐어요. 회귀 시험 TC-597·598과 TC-222가 에뮬레이터에서 통과했고, TC-222의 빠른 경로와 프로세스 회수 예비 경로는 [삼성 실기기](#bug-112-삼성-실기기-시험)에서도 통과했어요. 처음 기록은 `open`이었고, 신고한 폰에서 확인하면 `verified`로 바꿔요.
- 환경과 신고. 2026-11-22 11:00:44 UTC에 운영 `marong-app`이 0.3.1의 확인을 200으로 응답했고, 11:00:45에 코드 10인 0.3.2 APK를 전송했어요. 13:51까지 후속 업데이트 확인이나 기기 보고가 없었고, 사용자가 확인한 삼성 폰에는 0.3.1이 표시됐어요.
- 재현 대상은 Android 16에서 선톡 알림의 실행 인텐트로 앱을 열고 로컬 시험 서버에서 APK를 받은 뒤, 앱이 표시된 동안 설치를 보류하고 화면을 내려 자연 실행을 관찰하는 흐름이에요. 대기 버킷 `rare`, `restricted`와 강제 절전도 시험해요.

### BUG-112 에뮬레이터 시험용 APK 만들기

1. 저장소를 영문 경로의 임시 폴더에 복사하고 Java 21과 Android SDK 36을 지정해요. 복사본의 `apps/android/capacitor.config.json`에서 `server.url`을 `http://10.0.2.2:18787`로, `server.cleartext`를 `true`로 바꿔요. `apps/android/android/app/src/main/AndroidManifest.xml`의 `<application>`에 있는 `android:usesCleartextTraffic`도 `true`로 바꿔요. 복사본의 `apps/android`에서 `npm ci`와 `npm run sync`를 실행해요.
2. 복사본의 `apps/android/android`에서 `./gradlew :app:assembleDebug`(Windows는 `./gradlew.bat :app:assembleDebug`)로 만들고 `app/build/outputs/apk/debug/app-debug.apk`를 `target-10.apk`로 복사해요. `app/build.gradle`의 `versionCode`만 `9`로 바꿔 같은 명령과 같은 디버그 서명으로 `seed-9.apk`를 만들어 둬요. 두 파일은 일반 경로와 `fallback-busy-idle`에 써요.
3. `call`, `call-no-permission`, `call-dismissed`, `ring`에는 아래 수신기를 추가한 `call-9.apk`를 첫 설치에 써요. 복사본의 `apps/android/test/support/UpdateFixtureReceiver.java`를 `apps/android/android/app/src/main/java/com/corthexhq/marong/`에 복사하고, 복사본 매니페스트의 `<application>` 아래에 다음 항목을 넣어 `:app:assembleDebug`를 다시 돌려요. `android.permission.DUMP` 제한을 둬요.

   ```xml
   <receiver android:name=".UpdateFixtureReceiver" android:exported="true"
       android:permission="android.permission.DUMP" />
   ```

4. `reopen-at-commit`에는 같은 복사본의 `AppUpdateJob.java`에서 `install()` 안의 `Commit outcome = commitOnMain(...)` 줄 바로 앞에 `UpdateFixtureReceiver.pauseBeforeCommit();`을 넣고 다시 빌드한 `race-9.apk`를 써요. 업데이트 대상으로는 2번의 `target-10.apk`를 계속 써요.
5. Android 16 시험 AVD에서 `node apps/android/test/support/app-update-emulator.cjs <emulator-serial> <code-9.apk> <target-10.apk> <mode>`를 실행해요. 같은 AVD에서 다음 시험을 시작하기 전에 35초 이상 기다려요. 알림함을 직접 밀어야 하면 `MARONG_TC222_SHADE_PNG`에 임시 PNG 경로를 설정하고, 저장된 화면에서 `Fixture · 통화 중` 알림의 위치를 찾아 AVD에서 그 알림을 밀어요.

## 삼성 Remote Test Lab 확인 절차

Windows 시험 준비본은 `C:/tmp/marong-bug112/`의 `rtl-fixture.cjs`, `rtl-9.apk`, `rtl-10.apk`예요. 스크립트에 저장소의 `apps/android/test/support/emulator-site.cjs` 절대 경로와 두 APK를 순서대로 넘겨 실행하고, `offer`를 입력하면 코드 10을 제공해요. 로컬 시험 서버의 응답과 APK 크기·SHA-256 일치를 확인했어요. 에뮬레이터 초기 설치는 ADB를 썼어요. 에뮬레이터 브라우저에서 APK를 여는 명령은 자동 승인 검토가 `blocked by policy`로 거절했어요.

1. 노트북 브라우저에서 삼성 계정으로 로그인하고 Galaxy S26 Ultra의 Android 16(One UI 8.5)을 고릅니다. 가용 기기와 예약 상한은 기기별로 다릅니다. 준비와 15분 관찰을 고려해 가능한 경우 60분을 잡습니다. [Samsung 기기 목록](https://developer.samsung.com/remote-test-lab), [서비스 이용 조건](https://developer.samsung.com/terms?location=us#remote-test-lab)
2. 기기를 연 뒤 **Remote Debug Bridge → Connect**를 선택하고 화면에 RSA 요청이 뜨면 허용합니다. 노트북에서 `adb devices -l`로 해당 기기를 확인합니다. 삼성은 RDB의 일반 ADB 연결을 안내합니다. [Samsung RDB 연결 방법](https://developer.samsung.com/remote-test-lab/blog/en/2022/07/13/connect-to-devices-on-remote-test-lab-using-rdb-in-android-studio)
3. 노트북 루프백 시험 서버를 시작하고 `adb -s <RTL_SERIAL> reverse tcp:18788 tcp:18788`을 등록합니다. 기기 브라우저의 `http://127.0.0.1:18788/healthz` 응답으로 실제 왕복을 확인합니다. RDB에서 reverse가 동작하는지는 예약 세션에서 확인할 항목입니다. 운영 Access 계정과 운영 서명 키를 시험에 사용하지 않습니다.
4. 기기 브라우저에서 `http://127.0.0.1:18788/fixture/marong-test-9.apk`를 열어 코드 9 시험 앱을 설치합니다. 마롱이의 글 대화 메뉴에서 이 출처의 설치를 허용하고 앱은 알림을 허용합니다. 삼성 자동 차단과 배터리 설정의 상태를 기록합니다.
5. 같은 시험 키의 코드 10 APK를 시험 서버에서 제공하고 앱을 열어 다운로드 1회와 `adb -s <RTL_SERIAL> logcat -s MarongUpdate`의 `deferred` 및 `backup_scheduled`를 확인합니다. 홈으로 나간 뒤 앱을 열지 않고 `adb -s <RTL_SERIAL> shell dumpsys package com.corthexhq.marong`에서 15분 이내 `versionCode=10`을 확인합니다. 먼저 충전 상태로 확인하고, 새 설치로 초기화해 `rare`·`restricted` 및 강제 Doze에서 반복합니다. 같은 기기에서 업데이트 시도 간격을 35초 이상으로 두고, 갱신을 확인한 뒤 앱을 열어 글 대화를 봅니다.
6. 사용자 확인 경로는 새 설치에서 앱의 출처 설치 권한을 끄고 별도로 봅니다. `confirmation` 및 알림함의 무음 앱 업데이트 알림 301(SCR-130)이 한 번 뜨는지 확인합니다. 제목은 '마롱이 앱 새 버전이 있어요'이며 잠금 화면에서 내용을 숨기면 공개 제목 '마롱이 앱 새 버전'이 표시돼요. 누르면 Android 확인 화면이나 출처 허용 화면이 열려야 합니다. 권한이 제한되면 `confirmation_hidden` 또는 채널 설정을, 설치가 실패하면 `update_verify fail`과 `update_install fail`을 확인합니다. `committed` 뒤에도 버전 코드를 확인해서 최종 설치를 판정합니다.
7. 시험 앱과 받은 시험 APK를 제거하고 `adb reverse`를 해제합니다. TC-229의 이틀 관찰은 기기를 연속으로 예약할 수 있는지 확인한 뒤 별도로 진행합니다.

- 상태 · `fixed`. 2026-11-23 PR #111(`cafdb22`)로 합쳐졌고, 0.3.4 게시 전에 서버에 반영됐어요(배너는 서버가 내보내는 페이지라 APK는 그대로). 처음 기록은 '수정, 리뷰 대기'였어요. 심각도 · 중간. 받아 둔 버전이 있어도 배너에서 바로 설치할 수 없었어요.
- 재현 · 앱 연결 3과 준비된 시험 APK를 두고 배너 모듈 응답을 500ms 넘게 지연해요. 통화 단추나 첫 메시지 목록은 나타나지만 모듈 응답 뒤에도 배너가 숨은 채로 남아요. Android 16에서는 첫 선톡 알림으로 글 대화를 열고 APK를 받아 둔 다음 두 번째 알림으로 새 글 대화 화면을 열어요(TC-619).
- 근거 · 수정 전 Playwright의 통화 홈과 글 대화에서 각각 `locator.waitFor: Timeout 2500ms exceeded`가 나왔어요. 첫 화면이 그려진 뒤 모듈 응답을 풀었고, 다음 상태 변화 이벤트를 보내지 않았어요. Android 16에서 두 번째 알림으로 열린 활성 WebView에서도 `second_chat_module_ms=2104 banner_on_load=none`과 `second_chat_banner=none native=ready`를 확인했어요.
- 원인과 수정 · 최초 500ms가 지난 뒤 모듈이 로드되면 상태 읽기를 건너뛰었어요. 첫 화면이 이미 그려진 경우에도 모듈 로드 직후 500ms 한도로 상태를 한 번 읽어요. 배너가 뒤늦게 뜰 때는 기존 배치 처리를 사용해 마지막 말의 위치를 지켜요(SPEC-443).
- 원인 단계 · 11 개발. 명세 바뀜 없음: SPEC-439·443은 이미 받아 둔 버전이 있으면 #update-ready를 보이라고 요구해요(SPEC-439 ①, SPEC-443은 같은 규칙 ①\~④). 배너 모듈을 늦게 받은 화면에서 상태 읽기를 건너뛴 코드가 그 요구를 어겼고, 고침(모듈을 받은 직후 500ms 한도로 한 번 더 읽음)은 코드를 명세에 맞춘 것이에요. 마롱이 답(2026-11-23, PR #113 질문 1).
- 회귀 시험 · `apps/android/test/app-update-banners.e2e.cjs`의 `BUG-113 TC-609`(통화 홈)와 `BUG-113 TC-618`(글 대화) 두 개('a late module reads the staged update after the first content'). 고치기 전 `d46280d`에서 2개 실패, `cafdb22`에서 2개 통과했어요(PR #111). 에뮬레이터 쪽은 TC-619예요.
- 시험 환경 · `qa034-current-final.log`의 알림함 탐색 실패와 `qa034-current-after-shade.log`의 시험 주소 `//chat/` 오류는 별도의 시험 도구 문제예요. `qa034-current-origin.log`에서는 글 대화가 다시 열리고 네이티브가 `ready`를 돌려줬지만, 시험이 활성 WebView를 구분하지 않아 당시 화면의 정확한 원인은 그 로그만으로 알 수 없어요.
- 재시험 · Playwright 회귀 2개와 전체 73개 통과. Android 16에서 지연을 넣은 경우 `second_chat_module_ms=1388 banner_on_load=ready`, 지연을 주지 않은 경우 `second_chat_module_ms=995 banner_on_load=ready`였어요. 두 실행 모두 알림 2건과 통화 중 보류를 확인했고, 설치 단추를 누른 뒤 각각 0.663초와 0.526초에 코드 13을 확인했어요. 재실행 시험은 설치 직후 Android의 작업 정리와 겹치면 다시 열어 확인해요.
