# BUG-138 캐릭터 만들기 링크가 꺼진 기능으로 이동함

2026-11-28 KST 아이폰 웹 사용자 보고: '아 캐릭터 만들기 자체가 안되네'. 화면에 404 문제 JSON이 표시됐어요. 운영 접근 기록에서 해당 요청은 찾지 못해 실제 누른 경로는 확인하지 못했어요.

재현: 꾸미기는 켜고 캐릭터 만들기는 끈 뒤 기본 마롱이의 보관함에서 '캐릭터 만들기'를 눌러요. `/chat/character/new`로 페이지 이동하고 서버가 404 문제 JSON을 그대로 반환해요. SCR-183#default-marong의 링크 구현이 통합 앱 기능 명세 1절 9 공통 스위치 규칙(꺼진 기능 메뉴를 숨김)을 확인하지 않았어요. 승인 문서 변경은 없어요.

기존 TC-546은 꾸미기 스위치만 확인해 두 스위치가 서로 다른 조합을 놓쳤어요. 회귀 시험은 해당 조합의 링크 부재와 기존 캐릭터 기능 켜짐 조합의 링크 표시를 검사해요. 수정 전 `5c2575f`에서 링크 개수 1 대 기대 0으로 실패했고, 수정 후 Chromium 화면 시험으로 확인했어요. 운영 기기 확인은 반영 뒤 남아요.

## 운영 반영

- 사용자님이 항목 106에서 PR #145 병합과 운영 반영을 승인했어요. 리뷰 기준 `dd5cdb2261e92f8001a1ff12ba56aa577393b324`를 대조해 병합했고, 병합 커밋은 `9124522bc053582862a54c8792e2a02e33e5c533`이에요.
- 반영 전 운영 `decor.js` SHA-256은 병합 직전 main `5c2575f`와 같았어요. 앱 서버 파일을 백업하고 `~/marong-deploy/20261128-bug-138/rollback.sh`를 준비한 다음, 최근 120초 메시지·진행 중 통화·최근 resting 통화·열린 구간·벨이 각 0건일 때 2026-11-28 15:04:53 KST에 앱 서버를 재시작했어요. 되돌리기는 파일을 복원하고 이번 업데이트 내역을 지우며 앱을 재시작해요.
- 운영 파일과 서버 정적 응답 SHA-256은 병합본 `c75def2e413fc4a7ca731e7d54a97b33035240550167514df2bc48a76f83d857`와 같고, 정적 응답은 200과 `Cache-Control: no-store`예요. 조건부 링크 코드가 정적 응답에 있고 이전 무조건 링크 코드는 없어요.
- 비인증 보관함과 캐릭터 페이지는 302, 보관함 API는 401, health는 200, 서비스는 active였어요. 앱 웹 화면에는 서비스 워커 등록이 없고, 이미 열린 화면이 새 스크립트를 받아 표시하는 것은 실기기에서 확인하지 못했어요.
- 업데이트 내역 파일은 운영 판독기 검사에 통과했고 항목 1개와 반영일 2026-11-28을 확인했어요. 사용자님의 아이폰 확인은 아직 하지 않아 상태는 fixed예요.
- 5분 관찰: 06:04:53~06:09:56 UTC(303초)에 `journalctl -u marong-app --since "2026-11-28 06:04:53 UTC" --no-pager`의 ERROR·CRITICAL·Traceback 개수는 0건, `systemctl is-active marong-app`은 active, `curl` health는 200이었어요. 명령 출력은 당시 대화에만 있고 별도 서버 증거 파일로 보관하지 않았어요.

## 병합 절차 차이

- 확인된 원인: 작업자가 준비 완료, 추가 코드 리뷰 요청, 병합 명령을 `&&`로 연달아 실행했어요. 앞 명령의 성공은 요청 댓글이 만들어졌다는 뜻인데, 리뷰가 끝났는지와 결과를 확인하는 단계를 넣지 않아 곧바로 병합했어요. 따로 의도한 예외나 한도 실패가 있었는지는 확인된 근거가 없어요.
- GitHub 기록상 리뷰 요청은 2026-11-28 06:02:30 UTC, 병합은 06:02:33 UTC, 추가 코드 리뷰 결과는 06:03:25 UTC예요. 따라서 사후 결과는 병합 시점의 판단 근거가 아니었고, 그 사이에 발견됐을 수도 있는 문제를 병합 전 걸러낼 기회를 놓쳤어요. [병합 전 리뷰 댓글](https://github.com/kodonghui/marong2/pull/145#issuecomment-7235028596)은 06:01:19 UTC에 `dd5cdb2`를 검토해 수정이 필요한 문제를 발견하지 못했다고 적었지만 리뷰 수행 주체는 밝히지 않았어요. PR 설명에는 Claude 리뷰가 미확인으로 적혀 있어 그 댓글을 Claude 리뷰라고 확인할 수 없어요. 사후 병합 커밋 `9124522`의 추가 코드 리뷰는 06:03:25 UTC에 주요 문제가 없다고, 보안 리뷰는 06:04:47 UTC에 보안 문제가 없다고 보고했어요. 이 결과만으로 절차 차이가 없었던 것은 아니에요.
- 재발 방지: 병합 명령을 리뷰 요청과 연이어 자동으로 실행하지 않아요. 요청한 리뷰의 완료 상태·검토 커밋과 결과를 별도 조회해 확인하고, 발견 사항을 처리한 다음 현재 head를 다시 대조해 병합해요. 한도 실패가 확인된 경우에만 저장소의 예외 절차를 따르고 PR에 실패를 적어요. 리뷰가 대기 중이거나 상태를 확인할 수 없다면 병합하지 않아요.

## SPEC-503 업데이트 내역 증거

- 실제 절차: 반영 전 PR #146에 내역 JSON을 커밋하고 로컬 `tests/test_changelog.py`를 통과시켰어요. 반영 스크립트는 이를 `install`로 운영 폴더에 직접 복사한 뒤 앱을 재시작했어요. SPEC-503이 정한 재시작 뒤 `changelog put`을 쓰지 않았고, 그때 `changelog check`도 실행하지 않았어요. 따라서 반영 폴더에 내역 파일 사본·sha256 파일·`changelog.copied-at`은 없어요. 당시 Claude의 내역 문구 리뷰도 복사 전에 받지 못했어요.
- 2026-11-28 06:13:05 UTC에 운영 파일의 `stat`을 조회했을 때 파일 생성·수정·변경 시각은 모두 06:04:52.168560884 UTC(15:04:52 KST), 서비스 시작은 06:04:53 UTC였어요. 파일 시스템의 시각으로는 복사가 재시작 직전이며 한국 날짜는 JSON의 `deployedOn` 2026-11-28과 같다고 볼 수 있어요. 다만 이는 SPEC-503의 `put`이 남긴 복사 시각이 아니며, 독립 보존된 당시 복사 명령 출력도 없어 정식 날짜 대조를 통과했다고 말할 수 없어요.
- 06:13:24~06:13:25 UTC에 저장소와 운영 JSON의 `sha256sum`은 모두 `c39af9bde792ee2b8f45ae9ffd2f885d70ab240d801f4580c1fd4b1d7928c8d4`였고, 운영 `validate_unit`은 `valid=True`, 항목 1개와 `deployedOn=2026-11-28`을 반환했어요. 같은 시각 로컬 `/tmp/marong-admin-qa/bin/python tests/test_changelog.py`는 6개 통과했어요. 이 검사는 형식과 현재 파일 일치만 확인하며 정식 `check`를 대신하지 않아요.
- 06:13:24~06:13:25 UTC에 저장소 JSON을 표준 입력으로 서버의 `python -m marong.admin_changes check 20261128-bug-138 /home/opc/marong-deploy`에 전달했더니 `invalid deployment_record`, 종료 코드 1이었어요. 필요한 사본·해시·복사 시각 기록이 없어 정식 확인이 불가능한 상태예요.
- 후속: 내역 문구 리뷰를 마치고, 운영 변경 권한을 받은 뒤 실제 시각을 사용한 `changelog put`과 `check`를 수행하고 결과를 별도로 기록해야 해요. 나중에 실행하면 그 시각은 원래 복사 시각이 아니므로 과거 시각으로 만들어 넣지 않으며, 날짜가 달라졌다면 계약의 날짜 불일치 처리와 운영 승인에 따라 해결해야 해요. 이번 증거 보완은 운영 파일을 변경하지 않았어요.

## 업데이트 내역 check 실패의 영향 (2026-11-28)

- 원인: 공개 JSON의 필수 필드가 빠진 것은 아니에요. `check`는 먼저 반영 폴더의 `changelog.json`을 읽고 이어서 `changelog.sha256`과 `changelog.copied-at`을 확인하는데, 직접 복사한 탓에 세 파일 모두 없어요. `invalid deployment_record`는 필요한 반영 기록을 읽지 못할 때 나오는 공통 오류예요.
- 표시 영향: 06:15:37 UTC에 운영 `marong-app`은 active, health는 200이었고, 비인증 관리 화면과 API-300 `/chat/admin/api/changes`는 모두 403이었어요. 인증된 실제 HTTP 응답과 화면은 확인하지 못했어요. 06:16:50 UTC에 운영 코드와 데이터를 사용하고 서비스와 같은 OS 사용자로 API-300 처리 함수의 인증 부분만 가짜로 바꿔 직접 호출하니 200·51건·제외 0건·이번 ID 1건이었어요. 실제 인증과 HTTP 통신을 확인한 결과는 아니에요.
- 로그와 시작: 06:15:37 UTC에 재시작 이후 `journalctl -u marong-app` 로그 25줄을 세었고 ERROR·CRITICAL·Traceback은 0건, 내역의 `invalid`·`missing_dir` 로그는 0건이었어요. 시작과 health가 정상이었음을 확인했지만 다음 시작을 실제로 시험하지는 않았어요. 코드상 표시는 매 요청마다 공개 폴더의 JSON을 읽고 반영 폴더의 증거는 참조하지 않아요.
- 다음 반영: 도구는 ID마다 해당 반영 폴더를 찾으므로 이번 ID의 `check`·`rollback`은 기록 부족으로 실패해요. 다른 ID의 반영 기록을 찾는 처리는 이번 폴더를 사용하지 않아서 이번 실패가 다른 ID의 `put`·`check`를 직접 막는 조건은 코드상 없어요. 실제 다음 반영은 실행하지 않았어요.
- 복구안(미실행, 조작에는 승인 필요): 한국 시각으로 같은 날에 PR에 저장된 정확한 JSON을 써서 `MARONG_HOST=opc@100.87.95.40 bash deploy/ovh.sh changelog put marong/changelog/20261128-bug-138.json`, 이어서 `MARONG_HOST=opc@100.87.95.40 bash deploy/ovh.sh changelog check 20261128-bug-138`을 실행해요. `put`은 같은 반영 폴더에 서버의 실행 시각·JSON·해시를 기록하고 공개 JSON도 같은 내용으로 다시 써요. 나중에 실행한 시각은 원래 복사 시각이 아니에요. 날짜가 바뀌면 `deployedOn`과 달라 `check`가 실패하므로 과거 날짜인 것처럼 꾸미지 말고 처리 방침을 정한 뒤 실행해요. 관리 API는 매 요청마다 읽으므로 이 복구에 재시작은 필요 없어요.
- 되돌리기: `MARONG_HOST=opc@100.87.95.40 bash deploy/ovh.sh changelog rollback 20261128-bug-138`은 유효한 보관 사본이 있을 때 공개 JSON을 삭제해요. 등록 전에는 기록 부족으로 실패하고, 등록 후에는 이미 보이는 내역을 지우므로 실행 전에 대상 파일을 백업하고 표시를 되살릴 때는 백업 복원에 대한 별도 승인이 필요해요. 표준 rollback은 반영 폴더의 기록을 지우지 않고, 기존 `rollback.sh`는 제품 코드까지 되돌리므로 내역 등록만 취소할 때 쓰지 않아요.
