### 2.2 코드에서 찾은 원인(`main` `ad9f2f4`)

1. 받기가 페이지를 처음부터 다시 불러요. `MainActivity.openFromIntent`가 받기(ACTION_ANSWER)에서 `webView.loadUrl(PushLinks.ringUrl(...))`을 불러요. 앱이 꺼져 있었으면 시작 주소를 한 번 불러온 뒤 벨 주소를 또 불러요.
2. 모든 정적 파일이 캐시 없이 다시 받아져요. `server.py`가 `/face/v1/` 밖의 모든 응답에 `Cache-Control: no-store`를 붙여요. `livekit-client.js` 619,309바이트도 통화마다 새로 받아요. 이 작업 컨테이너에서 측정한 첫 바이트 시간은 파일마다 약 1.2초였어요. 폰에서 측정한 값은 아니에요.
3. 화면 코드가 619KB를 기다려요. `index.html`이 `livekit-client.js` → `rtc-client.js` → `worker-socket.js` → `app.js`를 모두 `defer`로 불러요. `defer` 스크립트는 순서대로 실행돼서, `app.js`는 LiveKit을 다 받은 뒤에야 돌아요. 그동안 화면은 기본 글과 기본 밤 테마예요. 사진 화면이 바로 이 상태예요.
4. 시작이 한 줄로 차례차례예요. `app.js`는 먼저 `/status`를 받고 그다음 프로필을 받은 뒤 `answerRing`을 불러요. `begin(true)`은 다음을 차례로 기다려요. LiveKit 연결 제한 시간은 12초예요.
   1. AudioContext
   2. 대기음 받기
   3. 재생 워크릿
   4. 마이크(`getUserMedia`)
   5. 녹음 워크릿
   6. `POST /api/rtc`
   7. LiveKit 연결
   8. `startAudio`
   9. `/live` 연결
   10. Gemini 연결 준비
   11. 첫마디
5. 측정이 없어요. 폰 쪽 단계 시각을 남기지 않아요. 서버의 `provider_ready_at`도 실제 준비 시각이 아니에요(BUG-110). 그래서 REQ-008(4초)이 맞는지 볼 수 없어요.

- 원인 단계: 04 명세에 '받기부터 첫 목소리까지 무엇을 동시에 하고 무엇을 기다리는지', '정적 파일 캐시', '시각 기록'이 없어요. 구현은 그 빈칸을 차례차례로 채웠어요. 고칠 명세는 SPEC-400\~403이에요.

### 3.2 원인

받은 목소리는 화면까지 왔는데, 폰이 그 소리를 내보내는 재생 단계에서 사라졌어요. 코드는 다음과 같아요.

- `rtc-client.js`는 받은 트랙을 숨겨진 오디오 요소 하나에 붙이고(`track.attach(this.element)`), `play()` 실패를 `catch(() => {})`로 버려요.
- 입을 움직이는 분석기는 같은 트랙을 따로 듣고, 소리를 0으로 줄여(`gain 0`) 내보내요.
- 그래서 오디오 요소가 재생을 시작하지 못해도 입은 움직이고, 화면은 그걸 모르고 소리만 안 나요.
- LiveKit의 재생 상태 신호(`AudioPlaybackStatusChanged`)는 처리하지 않아요.
- 재생이 실제로 소리 장치까지 나갔는지 보는 값(WebRTC 통계의 `media-playout`)도 읽지 않아요.

남은 후보와 가르는 법:

| 후보 | 가능성 | 가르는 법 |
| --- | --- | --- |
| 가. 오디오 요소가 재생을 시작하지 못함(자동 재생 막힘, 페이지 다시 불러오기 뒤 멈춤 등) | 가장 높음. 실패를 버리는 코드라 지금 기록으로는 안 보임 | 요소의 `paused`, LiveKit `canPlaybackAudio`, `media-playout`의 재생 샘플 수가 늘어나는지(SPEC-404) |
| 나. 출력 장치나 볼륨: 통화 모드 소리가 들리지 않는 곳으로 가거나 통화 볼륨이 0 | 중간. 앱 코드는 출력 장치를 정하지 않음. Chromium은 통화 모드에서 유선 → USB → 블루투스 → 스피커 순으로 고름(Chromium `CommunicationDeviceSelector`) | 앱이 고른 출력 장치와 통화 볼륨을 진단에 남김(SPEC-403) |
| 다. 블루투스 | 아님 | 원문3 |

- 원인 단계: 04 명세에 '목소리가 실제로 재생되는지 확인하고, 안 되면 다른 경로로 바꾸기'와 '앱의 출력 장치 규칙'이 없어요. 통화 명세 SPEC-003·005는 OpenAI 경로 때 것이고, 기능 명세 [spec.md](../04-functional-spec/spec.md) 7.1의 4번 '스피커폰·이어폰·블루투스 소리 경로'는 지금 경로(Gemini + WebRTC)에서 시험하지 않았어요. 앱 벨 시험 [app-ring.md](../app-ring.md) TC-147(에뮬레이터)은 마이크 소리만 봤어요. 고칠 명세는 SPEC-403·404예요.

## 4. BUG-110 통화 기록의 준비 시각과 구간 종류

- 실제: `call_memory.start_segment`가 Gemini 연결(`open_provider`)보다 먼저 구간 줄을 `state='open'`, `provider_ready_at=now()`로 넣어요. 새 통화의 첫 구간도 종류가 늘 `reconnect`예요.
- 기대: `provider_ready_at`은 Gemini가 `setupComplete`를 보낸 때이고, 새 통화의 첫 구간은 `start`예요.
- 영향: 준비 시간(Gemini 연결)과 첫마디 시간을 기록에서 나눌 수 없어요. 구간 종류로 다시 연결 횟수를 세면 첫 구간까지 세어져요.
- 고칠 명세: SPEC-400(05 표의 칸 뜻을 같이 적음).
